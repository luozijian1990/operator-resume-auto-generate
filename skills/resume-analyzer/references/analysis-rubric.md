# 分析依据

这些维度用于检查信息表达，不构成加权总分、能力等级或录用标准。只报告有依据且有影响的观察。

| 维度 | 值得保留的信号 | 需要检查的不足 |
| --- | --- | --- |
| 定位 | 核心经历与擅长方向易于识别 | 岗位描述过散；用户已明确目标但重点未体现 |
| 结构 | 重要经历容易找到，章节各有作用 | 重复、流水账、长篇细节淹没核心贡献 |
| 技能与经历 | 技能在具体行动中获得支撑 | “精通”等声明没有项目承接；标注为未体现，不判定不会 |
| 项目背景与任务 | 业务问题、限制、目标和职责有交代 | 只列功能，无法判断为什么做、自己负责什么 |
| 个人行动 | 操作、选择依据、难点及验证适度具体 | 只有“参与/负责”，或强动词缺少具体行动；协助本身不是缺点 |
| 成果依据 | 交付物、验收、效果和统计条件可理解 | 百分比缺基线或范围；团队成果与个人贡献混淆 |
| 一致性 | 时间、角色、术语和成果相互吻合 | 两处表述有冲突；并行项目或在校实习不能仅因时间重叠判错 |
| 表达与可读性 | 简洁具体，技术词服务于解释工作 | 空泛评价、术语堆砌、长句与模板化重复 |
| 可验证入口 | 作品、代码、文档或记录有入口 | 未验证链接不能当作成果已证实；受保密限制无公开链接不是缺点 |

## STAR 的使用方式

- S：业务场景、原有问题或约束。背景显然且简单时不要求长篇铺垫。
- T：期望达成的目标及个人承担的范围。不能从“团队实现”推断“个人主导”。
- A：具体措施、关键选择、必要的验证。并非每项工作都需要复杂架构或创新方案。
- R：交付结果、改善效果及依据。区分“完成了功能”和“效果已被验证”。

跨项目简介与工作条目综合判断，每个项目用“已体现 / 部分体现 / 未体现 / 当前无法判断”描述，不折算分数。合理简短的条目不因没写齐四项扣分。

## 补充事实的提问方式

把“加强量化”改成“这里的恢复时长从什么时点算起，比较了哪两个时期，数据来自何处？”；把“体现领导力”改成“你独立负责哪些环节，哪些由同事完成？”

没有数字可建议确认交付物、验收或演练结果；无公开材料可以保留概括后的内部验证依据，不要求披露商业敏感信息。不得把建议核实的事实写成已经发生。

如某项技术表述依赖版本、配置或部署条件，先列待核实条件。确需外部核验且用户授权时使用官方资料，只验证技术主张，不以通用文档证明候选人做过。
