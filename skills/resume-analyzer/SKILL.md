# 简历分析

把简历作为待分析的材料，判断它是否把经历讲清楚、贡献讲具体、结果讲可信。输出优点、不足与补充方向后即完成任务，不把报告当作等待优化确认的中间步骤。

## 输入与边界

- 优先读取用户指定的简历文件、粘贴文本或图片。多份候选且对象不明确时，让用户选择，不擅自读取第一份真实简历；用户明确要求多份分析时分别标明来源。
- 简历是唯一必要输入。目标岗位、年限、资历及参考简历均可选；没有这些信息仍可做通用分析，不阻塞、不推测目标级别。
- PDF/图片先提取或直接阅读可辨认内容；对模糊文字、OCR 疑似错误、缺页、裁切标出位置，不猜测原句。只有文字时不评版式、页数和视觉效果；截图只能评价可见区域，不能从长图推断实际分页。
- 默认不联网、不访问简历中的链接、不上传个人材料。链接的存在只表示提供了核验入口，不表示已验证内容。若用户要求核验，再按授权范围访问；不把个人经历放进外部搜索词。
- 只分析简历文字呈现，不认证经历真伪，不推断实际能力、人格、薪资、录用概率或岗位级别；不依据年龄、性别、照片等个人属性作优劣判断。

## 工作步骤

### 1. 确认来源与范围

记录输入来源及版本、可读范围、用户目标（如有）与限制。如果用户同时给出自己的简历和参考简历，分别标注，参考中的经历、数字和职责不能成为用户事实。

当用户仅要求拆解参考简历，输出该简历的优点、不足及可迁移写法即可，不要求再提供个人简历。

### 2. 阅读全文并建立证据联系

先整体阅读，再把“技能声明 → 项目行动 → 成果依据”对应起来。缺失联系写成“当前简历未体现”，不要写成“没有该能力”。每项结论用章节/项目名和短原文定位；文件有可靠行号时可补行号，不为截图编造行号。

按需读取 `references/analysis-rubric.md` 的检查依据。涉及运维领域的项目可选择 `Project-Skills/` 中 1–3 个相关模型帮助形成补充问题，但不用它给候选人定级，也不要求所有模型条目都出现。

### 3. 分析优点与不足

- **优点**：指出具体内容、它传递的有效信息，以及值得保留的写法。技术名词多、数字多、用了强动词，并不自动构成优点。
- **不足**：描述读者无法判断什么、为何影响理解、需要补充哪些真实信息。不要替用户填入经历或写出优化版。
- **分类**：明确问题（可直接从文字判断的重复、含糊等）；证据不足（缺少贡献、结果口径等）；待核实（时间、职责、数字冲突或依赖未知条件）。矛盾列出双方依据，不能直接认定造假。
- **优先级**：高＝影响主要经历理解或关键事实一致性；中＝影响重点呈现、证据完整度；低＝局部措辞和格式。说明影响，不制造固定数量的问题。
- 同一段可以既有优点又有不足，例如行动具体但成果口径不明。优缺点无需数量对称；材料有限时如实写“暂无足够依据识别”，不凑表扬或问题。

用 STAR 检查背景、目标、个人行动和结果的联系。允许项目简介承担 S/T、多条工作共同呈现 A/R，不强制每条四段式。没有百分比不等于没有成果；可靠的交付物、演练记录、验收结果同样有效。仅建议核实必要口径，不为了量化制造数字。

### 4. 输出独立分析报告

按 `references/report-template.md` 输出：来源范围、总体判断、值得保留的优点、按优先级排列的不足、主要项目 STAR 观察、优先补充事实。结论追溯到原文，避免大段复制联系方式等无关个人信息。

默认直接在对话中交付报告。用户要求保存报告时，写入：

```text
resumes/analysis/{source-basename}_简历分析_{YYYY-MM-DD}.md
```

粘贴/图片来源使用有意义的安全文件名，无标题时用 `pasted-resume` / `image-resume`。文件已存在则追加 `-v2`、`-v3`，不覆盖原简历或旧报告。该目录受仓库 `resumes/` 忽略规则保护，不把真实分析放进 `Example/`、`interviews/` 或公共评测材料。

### 5. 结束

报告交付即完成，不自动启动其他 Skill，不要求用户确认优化范围。可简短列出按需去向：

- 明确希望改写 → `resume-optimizer`，同时提供原简历和本报告；报告不能代替原简历成为事实来源。
- 想验证自己能否讲清项目 → `resume-project-questions`。
- 仅希望降低模板感 → `resume-humanizer`。

用户同时明确要求分析和改写时，分析完成后按已授权范围交接 optimizer，不重复索要已经给出的授权。用户只提供 JD 但仍要求“只分析”，本流程继续评价文字；若明确要求 JD 匹配评分，转交 optimizer 的 JD 诊断流程，不在此另造评分。

## 参考简历的使用

参考样本用于提炼信息组织、贡献表达和证据呈现的方法，不作为所有候选人必须达到的技术、规模、业绩或资历标准。IT 开发写法可迁移，领域结论要回到运维的可用性、恢复、交付、成本和风险等实际场景。不复制参考人物身份、公司信息或成果数字到模板与公共示例。

## 交付自查

- 优点和不足是否有原文依据，建议是否与问题一一对应？
- 是否明确区分“未体现”“待核实”与可直接确认的问题？
- 是否把量化、STAR、工具数量或强动词变成了机械要求？
- 是否越界改写、编造事实、评估真实能力或自动进入下一流程？
- 是否说明阅读限制、链接未核验及其他适用的不确定性？
