# 中文技术简历去 AI 化

## 目标与边界

把简历改得像真实候选人的工作记录，而不是换一批同义词掩盖 AI 痕迹。优先恢复可追问的经验细节；没有事实时追问、降级或删除，禁止补写虚构的指标、踩坑、决策和职责。

只处理中文运维、SRE、DevOps、平台工程简历。保留英文技术名词、产品名、命令和参数。本 Skill 不负责重新做 JD 匹配、调整项目顺序或生成完整面试题。

不要输出“AI 生成概率”或承诺规避检测。只评估文本的模板化和可信度风险。

## 必读参考

处理任何简历前，先阅读 [`references/resume-patterns.md`](references/resume-patterns.md)，按其中的风险模式、分区规则和改写原则执行。该文件已经包含本 Skill 所需规则，不依赖外部 `humanizer-zh`。

## 工作流

### 步骤 0：确认输入

按以下优先级确定源简历：

1. 用户明确指定的文件；
2. 用户直接粘贴的简历正文；
3. 列出 `resumes/` 中的候选文件，等待用户选择；
4. 仅在用户明确要求演示或验证时使用 `Example/`。

多份候选时禁止自动选择最新文件。链接无法读取时，请用户粘贴正文。

目标 JD 是可选输入：

- 没有 JD：执行通用去 AI 化；
- 有完整 JD：冻结简历中已经真实命中的 ATS 关键词；
- 只有用户明确给出的关键词保护清单：按清单保护已有词，不把它当成完整 JD，也不判断覆盖率；
- 只有公司名、岗位名或级别：不推测 JD 内容，按无 JD 处理。

🔴 **CHECKPOINT · 🛑 STOP：源简历未唯一确定前，禁止诊断或写文件。**

### 步骤 1：建立事实冻结表

先读取完整简历，再提取禁止擅自改变的事实：

- 公司、岗位、时间线、教育和证书；
- 技术栈、产品名、命令、版本和架构组件；
- 数字、单位、比例、规模、故障和业务结果；
- `主导 / 负责 / 参与 / 协助` 等职责等级；
- 有 JD 时，已经在简历中出现且有事实支撑的 ATS 关键词。

把源简历里的陈述视为“保留但未核验”。只有用户明确确认的内容才算“已确认事实”。发现前后矛盾、异常整齐的数字或职责倒挂时，只标记风险，不自行纠正。

### 步骤 2：先输出诊断

在对话中输出诊断，不写文件：

```markdown
## 简历去 AI 化诊断

### 总体判断
- 最明显的模板化信号：
- 最大可信度风险：
- 建议处理范围：

### 风险评估
| 维度 | 风险 | 原文证据 | 处理建议 |
|---|---|---|---|
| 模板化表达 | 低/中/高 | 短句引用或章节位置 | ... |
| 事实可追溯性 | 低/中/高 | ... | ... |
| 职责可信度 | 低/中/高 | ... | ... |
| 经验独特性 | 低/中/高 | ... | ... |
| 面试可承接性 | 低/中/高 | ... | ... |

### 冻结项
- 事实与数字：
- 技术术语：
- JD/ATS 关键词（如有）：

### 需要补充的事实
1. ...

### 建议改写范围
1. ...
```

不要伪造精确分数。每个中高风险判断都必须引用具体句子或章节位置。

### 步骤 3：补充必要事实并确认范围

只追问能改变高风险结论的 3–5 个高价值问题，例如：

- 为什么采用这个方案，而不是当时可选的另一种方案？
- 你本人负责哪一段，哪些工作由团队其他成员完成？
- 这个数字从哪里统计，观察窗口是什么？
- 上线或故障处理中遇到过什么具体限制？

不要为了“增加灵魂”索要无关故事。用户无法补证的强表述，提供三种处理方式：补证后保留、降级表达、删除。用户不选择时，默认降级到现有事实能够支撑的最保守表达。

回显最终改写范围和冻结项，等待明确确认。

🔴 **CHECKPOINT · 🛑 STOP：用户未确认改写范围前，禁止生成新文件。若用户只要求诊断，到此结束。**

### 步骤 4：生成去 AI 版

按以下规则改写：

1. 保持公司、岗位、时间线和项目顺序不变；
2. 保持冻结事实、数字、技术名词和 ATS 关键词不变；
3. 默认把显式 `Situation / Task / Action / Result` 标题改为自然项目要点，但用户有固定模板时保留；
4. 用问题、约束、动作、取舍和结果之间的因果关系替代空泛结论；
5. 让项目长短由真实信息量决定，不强制每个项目三条行动、三个结果或同样字数；
6. 不新增用户没有提供的方案比较、故障细节、指标来源或个人贡献；
7. 不在最终简历正文中保留 `[待确认]` 等编辑标记，未解决风险放到交付说明；
8. 不生成完整面试题，只标出无法承接追问的表述。

分区处理：

- 个人简介：删除自我评价套话，保留年限、方向和可验证强项；
- 技能清单：减少“精通 / 熟练掌握”堆叠，不随意改写技术名词；
- 工作与项目经历：重点处理模板化 STAR、职责边界和事实支撑；
- 教育、证书、联系方式：只做明显格式修正，不改内容；
- front matter：保留已有字段，并追加本次处理元数据。

### 步骤 5：写入新文件

真实简历只写入 gitignored 的 `resumes/`，永不覆盖原文件。命名规则：

```text
resumes/{source-basename}_去AI版_{YYYY-MM-DD}.md
resumes/{source-basename}_去AI版_{YYYY-MM-DD}-v2.md
```

粘贴文本使用：

```text
resumes/pasted-resume_去AI版_{YYYY-MM-DD}.md
```

保留已有 front matter，并追加：

```yaml
humanizer_schema_version: v1
humanizer_source: resumes/source.md
humanizer_generated_at: "YYYY-MM-DDTHH:MM:SS+08:00"
humanizer_jd_source: null
humanizer_unresolved_risks: 0
```

时间使用实际当前时间。`humanizer_jd_source` 写用户提供的来源；无 JD 时为 `null`。

### 步骤 6：交付与验收

交付时只输出：

- 新文件路径；
- 3–8 条代表性修改对照；
- 已保护的 JD/ATS 关键词（如有）；
- 已降级或删除的高风险表述；
- 仍未解决的事实风险；
- 建议下一步运行 `mock-interview`。

不要在对话中铺开整份逐句对照。完整变化由用户查看源文件与新文件的 diff。

改写版必须同时满足：

- 没有新增事实；
- 冻结事实、职责等级和关键词没有漂移；
- 五个风险维度均无高风险项；
- 未解决风险已经在交付说明中列出；
- 语言自然但仍保持技术简历的专业和紧凑。

## 禁止事项

1. 不把“参与”改成“主导”，不把学习经历写成生产实践；
2. 不为增强可信度编造踩坑、方案取舍、统计口径或业务结果；
3. 不机械替换“负责、推动、提升、体系、闭环”等词，先判断上下文是否具体；
4. 不主动调整项目顺序或重新计算 JD 匹配度；
5. 不使用第一人称、情绪化表达、幽默、Emoji 或文章式“个人观点”；
6. 不依赖外部 AI 检测器，也不承诺面试官无法判断文本来源；
7. 不覆盖源文件，不把真实简历写进 `Example/`；
8. 不跳过诊断与用户确认门直接改写。
