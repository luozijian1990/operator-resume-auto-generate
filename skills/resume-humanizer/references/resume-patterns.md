## 一、风险模式

### 1. 显式 STAR 答题模板

连续使用 `Situation / Task / Action / Result` 标题，或每个项目都严格按同样四段展开，会让简历像训练样例。保留 STAR 的因果逻辑，默认把标签改成自然项目要点。

不要为了隐藏标签而丢掉背景、个人动作或结果。

### 2. 空泛的体系化结论

关注“构建完善体系、形成完整闭环、全面提升、显著增强、赋能业务、保障稳定”等没有对象和证据的表达。

- 有具体动作和结果：保留必要术语，压缩套话；
- 没有具体动作：追问；
- 无法补证：降级或删除。

### 3. 技术名词购物清单

单句罗列 Kubernetes、Prometheus、Grafana、ELK、Jenkins、Argo CD 等工具，却没有说明各自解决的问题、连接关系和个人工作。不要删除真实技术词；把它们放回具体动作和约束中。

### 4. 过度整齐的数字

每个项目都恰好包含三项结果、整数百分比或相似提升幅度时，标记统计口径风险。异常整齐不等于虚假，禁止擅自改数；询问基线、观察窗口和数据来源。

### 5. 职责动词膨胀

“主导、牵头、从 0 到 1、全面负责”必须与决策权、实施范围和协作边界一致。证据不足时保留原句但标高风险，确认后再保留、降级或删除。

### 6. 动作与结果断裂

“部署了 Prometheus，因此稳定性提升 99%”缺少指标定义和因果链。追问监控覆盖、告警变化、故障发现时间或统计方式。不要替用户补齐中间事实。

### 7. 机械三段式与等长项目

所有项目都使用三个动作、三个结果、相同句长和相同动词，会放大模板感。项目要点数量由信息量决定；两条、四条或六条都可以。

### 8. 宣传式自我评价

“具备深厚技术功底、卓越沟通能力、丰富实践经验、极强责任心”通常不可验证。替换为年限、负责范围、系统规模或稳定的专业方向；没有事实则删除。

### 9. 同义词循环

同一份简历为了避免重复而交替使用“搭建、构建、打造、建设、落地”，并不会更自然。允许准确动词重复，优先保证职责和动作一致。

### 10. 面试承接断层

强结论无法回答以下任一问题时，标记高风险：

- 你本人具体做了什么？
- 为什么这样选？
- 当时有什么限制？
- 数字如何统计？
- 失败时如何发现和回退？

这里只标风险，不生成完整面试题。

## 二、分区规则

### 个人简介

保留目标方向、工作年限、核心领域和有证据的规模信息。删除性格评价、愿景宣言和“全面掌握”式结论。

### 技能清单

保留技术名词与真实熟练度。避免每项都写“精通”；必要时按“生产使用 / 项目实践 / 了解”区分，但不能替用户判定等级。

### 工作与项目经历

优先保留：业务或技术问题、个人职责、关键动作、约束或取舍、可核验结果。默认隐藏 STAR 标签，不隐藏逻辑。

### 教育、证书和联系方式

只修正明显格式问题。不要润色证书名称、院校、时间和个人信息。

## 三、改写示例

### 空泛结果

改写前：

> 构建完善的可观测性体系，全面提升系统稳定性，形成监控告警闭环。

事实充分时可改为：

> 为 32 个微服务接入 Prometheus 指标和分级告警，并补充告警负责人和升级规则；上线后以用户提供的实际口径描述变化。

如果“32 个微服务、分级规则、变化口径”不是用户事实，就不能使用这句，只能追问或删减。

### 职责膨胀

改写前：

> 从 0 到 1 主导公司 Kubernetes 平台建设。

用户只负责监控模块时，降级为：

> 参与 Kubernetes 平台建设，负责集群监控与告警接入。

### 技术堆叠

改写前：

> 熟练掌握 Kubernetes、Helm、Prometheus、Grafana、ELK、Jenkins、Argo CD。

不要凭空拆成项目事实。先确认哪些用于生产、本人做过哪些配置和排障，再按真实使用场景组织。

## 四、事实保护检查

改写前后逐项对照：

1. 公司、岗位、日期是否一致；
2. 技术名词、版本、命令是否一致；
3. 所有数字、单位和比较基线是否一致；
4. 职责动词是否升级；
5. JD/ATS 关键词是否被误删或换成不等价表达；
6. 是否出现源文和用户补充中都不存在的新事实。

任何一项无法确认时，不交付为“已完成”；先修正或列为未解决风险。
