# 跨场面试聚合复盘 Skill

## 适用场景

用户已经用 `mock-interview` 跑了 ≥2 场面试，希望把这些数据**横向打通**，看清楚：

- 跨场维度评分（同一维度多场表现，比单场更稳定）
- 反复暴露的能力短板（出现 2+ 次的卡壳点是真问题，单场可能是状态波动）
- 简历看起来 vs 实际表现的系统性偏差
- 下一步该补什么（按 ROI 排序）

典型触发：

- "把最近这周的几场面试一起总结一下"
- "我面了 5 家，帮我看下整体啥水平、最该补哪些"
- "复盘一下昨天和前天那两场"

**单场不该跑这个 skill** —— 单场不足以聚合，结论会有偏差。skill 启动时强制要求 ≥2 场，仅 1 场时拒绝并提示用户继续积累。

---

## 核心设计原则

1. **聚合复盘 ≠ 单场总结**。本 skill 处理的是"几场面试横向对比"，不是"某一场面试的精细打分"
2. **记录文件只读，不写**。所有产出去到独立的聚合文件 `interviews/{date}-summary.md`，记录文件保持冻结
3. **每条结论可追溯**。卡壳引用必须标注 `[date 公司 Q{n}]` 来源，方便人工核对
4. **picture-in-time**。每次跑都是当下视角的截图——同一场面试可以在多份 summary 里重复出现

---

## 步骤 0：选定要聚合的面试

启动时**必须由用户显式选定**，绝不默认全量。

### 0.1 列出候选

扫 `interviews/` 目录，列出所有满足条件的记录文件：

- 文件名匹配 `{YYYY-MM-DD}-*.md`，但**排除** `*-summary*.md`
- front matter `status: completed` 或 `status: aborted`（`in_progress` 跳过）
- **默认推荐最近 30 天**——展示时按日期倒序，前 30 天的高亮"推荐"

展示格式：

```
找到 N 场已完成面试。请选择要纳入本次聚合的（默认推荐近 30 天）：

[1] [推荐] 2026-05-10  阿里 SRE P7         (8 题, status: completed)
[2] [推荐] 2026-05-08  字节跳动 SRE P6     (8 题, status: completed)
[3]        2026-04-20  腾讯 SRE 高级        (6 题, status: completed)
[4]        2026-04-15  美团 SRE 中级        (5 题, status: aborted)

请回复要纳入的编号（如 "1,2" 或 "全部推荐" 或 "全部"）。
```

### 0.2 等待用户选择

**用户不明确回复就停**，不要替用户做决定。允许的回复：

- 编号列表（`1,2` / `1-3`）
- 关键词（`全部推荐` / `全部` / `近 7 天` / `5 月所有`）
- 取消（`算了` / `不聚合`）→ 退出

### 0.3 强制 ≥2 场

用户最终选出的列表 `len < 2` 时拒绝：

> 选定 {N} 场，聚合至少需要 2 场。请继续用 `mock-interview` 再面 {2-N} 场，或调整选择。

**不**靠扩大默认范围来凑数——尊重用户意图。

---

## 步骤 1：读取与校验

按用户选定的 `interview_id` 列表逐一读取记录文件：

- 校验 `schema_version: v1`，不匹配的文件标出并询问用户是否跳过该场（不要强行处理未知 schema）
- 校验 `status` 在 `completed` / `aborted` 内
- 收集每题数据：题号、维度、题目、回答要点、卡壳原话、追问、评分

`aborted` 的场也纳入聚合，但在 `tags` 加 `aborted-included` 标记，且整体评分计算时该场的 `question_count` 权重正常使用（短场天然权重小）。

---

## 步骤 2：聚合计算

### 2.1 整体评分 `overall_score`

跨场所有题目评分的**加权均值**——每题等权，长场权重自然大。

```
overall_score = sum(每场所有题评分) / sum(所有场题数)
保留 1 位小数
```

### 2.2 维度评分 `dimension_scores`

收集每场的 `dimensions` 并集，对每个维度：

- 该维度在所有场出现题目的评分均值（保留 1 位小数）
- 该维度某场未覆盖时不计入分母
- 全场都未覆盖时写 `N/A`

同时算 `dimension_coverage`：该维度被几场覆盖。

### 2.3 Top Gaps（**层次加权**排序）

按"严重 × 高频 × 层次深度"三因素排序——**层次深度越浅的问题越严重**：L1 都过不去说明认知缺口，比 L3 才卡（边界思考不足）严重得多。

排序优先级（从高到低）：

1. **L1 fail 维度**：任一维度的 L1 通过率 < 0.5，说明连基础认知都不稳。**单独成段，标红色**
2. **致命缺项**（任一场 `match_breakdown.critical_gap.note` 提到的 JD 强必须项，且本人未答好）
3. **L2 系统性 fail**：维度评分 ≤ 2.5 且被 ≥2 场覆盖，且 L2 通过率 < 0.4（系统性实操短板）
4. **同一主题卡壳 ≥2 次**（高频盲区——比单次更可信）
5. **L3 fail**：仅当 L1/L2 都过的维度，L3 才卡的；权重最低（属于"已经不错但还能更好"）
6. **某场单点最差**（评分 ≤ 2 的题，作为补充）

每条格式：

```
{描述}（{出现场次}场暴露 / 最深卡在 L{n}）
```

例如："系统设计能力不足以支撑 P7 级岗位（2/2 场暴露 / 最深卡在 L2）"。`最深卡在 L{n}` 字段是新增的层次信号——读者一眼能看出这是"概念缺口"还是"实操缺口"还是"边界缺口"。

### 2.4 卡壳点回顾（标注来源 + 层次）

按维度归类。每条原话必须标注**来源 + 层次**：

```
[{date} {公司缩写} Q{n} L{layer}] > "{逐字原话}"
```

例如：`[2026-05-08 字节 Q1 L1] > "..."` 表示该卡壳发生在字节场 Q1 的 L1 层（基础认知层就卡了，说明严重）。

公司缩写从 `jd_company` 截取（如"字节跳动" → "字节"，"alibaba" → "Alibaba"）。多场出现同主题卡壳要全部列出，不要合并。

**末尾加一行 `· 层次分布`**总结该维度的卡壳层次：

```
- **{维度}**
  - [2026-05-08 字节 Q3 L1] > "..."
  - [2026-05-10 阿里 Q5 L2] > "..."
  - · 层次分布：L1 ×1 / L2 ×1 / L3 ×0 → 该维度 50% 在 L1 就卡，认知层缺口
```

这个层次分布提示让"卡壳点回顾"段不只是 quote 列表，而是诊断信号。

### 2.4.5 层次穿透率 `layer_pass_rate`

利用记录文件的钻孔式分层数据（L1/L2/L3），计算跨场的层次表现——比单 score 多一个"撑得到几层"的能力深度信号。

对每一层（L1/L2/L3）按如下规则统计：

| 字段 | 计算方式 |
|---|---|
| `reached` | 进入该层的题数（L1 = 所有题；L2 = 实际追问到 L2 的题数；L3 = 实际追问到 L3 的题数） |
| `passed` | 该层被评估为 ≥ 3 分（含 L1 OK 但 L2 卡的也算"L1 passed"）的题数 |
| `rate` | `passed / reached`，保留 1 位小数；reached=0 时写 `null` |

**判定 "L{n} passed" 的规则**：题目的"本题评分"理由中说明"L{n} OK"或更高层才卡的，视为 L{n} 通过。如评分理由"L1 OK，L2 起卡，L3 直接断"→ L1 passed, L2 not passed, L3 reached but not passed。

**层次穿透率告诉你什么**：

- L1 通过率高 + L2 通过率低 → "懂概念但缺实操"
- L2 通过率高 + L3 通过率低 → "实操扎实但缺边界思考"
- L1 通过率本身就低 → "认知地图缺口大，连基础都不稳"

这个信号在 Top Gaps 排序和 study_plan 生成时也要参考——L1 都过不去的维度优先级高于 L2 卡的。

### 2.5 "更强的人会怎么答"（**按卡的层次给针对性建议**）

针对评分 ≤ 2 的题（系统性短板优先），按所属场标注源题号 + 卡的层次。**关键：卡在不同层需要不同的补法**——

| 卡在哪层 | 短板性质 | 补法 |
|---|---|---|
| L1 卡 | **认知地图缺口** | 补**知识结构**——读经典教材、画概念地图、先把名词搞懂 |
| L2 卡 | **实操经验空白** | 补**真实项目**——动手做、踩坑、学具体命令/参数；读书没用 |
| L3 卡 | **边界思考不足** | 补**case study**——读大厂故障复盘、思考极端场景、学权衡决策 |

每条格式：

```
**[{date} {公司} Q{n} · 卡在 L{n}]**：{标准答题路径}
- 思路结构：{先讲什么再讲什么}
- 关键术语和工具链：{...}
- 加分延伸：{...}
- **补法方向**：{基于卡的层次，给出"读书 / 动手 / case study"中的一种}
```

不要为每题都写，只写**明显短板**——一般 3-5 条。

### 2.6 补课优先级 `study_plan`（**reason 引用层次数据**）

按 ROI 排序——**层次深度越浅 + 高频考点 + 多场暴露 = P0**。

| 优先级 | 含义 | 命中规则 |
|---|---|---|
| P0 | 立刻必补 | 致命缺项 / 跨 ≥2 场维度 L1 通过率 < 0.5 / 单场 L1 fail 但是 JD 强必须项 |
| P1 | 影响整体评分 | L2 通过率 < 0.4 且涉及 ≥1 个 JD 加分项 / 跨场维度评分 2.5-3.5 |
| P2 | 锦上添花 | L3 卡或表达问题 / 单点细节 |

每条 4 字段：`{priority, topic, reason, action}`

- `reason` **必须引用层次数据**：用 `L{n} 通过率 X/Y` 这种精确表达，比"评分 2.5"信息量大得多
- `action` 必须**对齐 2.5 表里的补法方向**——L1 卡 → 给读书路径；L2 卡 → 给实操项目；L3 卡 → 给 case study

反面例子（不要这样写）：

```
{priority: P0, topic: K8s 故障排查实战, reason: "评分 2.7 较低", action: "多刷题"}
```

正面例子：

```
{priority: P0, topic: K8s 故障排查实战, 
 reason: "K8s 排障维度 L2 通过率 0/3，是典型实操短板而非认知短板",
 action: "本地搭 5 节点 K8s，跑 6 个故障场景：CrashLoopBackOff/OOMKilled/NotReady/Pending/ImagePullBackOff/网络不通。每个场景手动复现 + 排查 + 写复盘"}
```

### 2.7 表达问题

观察跨场的语言特征：填充词频率、结构词缺失、回答耗时、自信度。**只有跨场重复出现的问题才列**——单场只算偶然。

### 2.8 tags

按 `interviews/SCHEMA.md` 中 tags 命名约定生成：

- 维度弱标记：`{维度小写}-weak`（当该维度 dimension_scores ≤ 2.5）
- 维度强标记：`{维度小写}-strong`（≥ 4）
- **层次画像标记（新）**：根据 `layer_pass_rate` 各层 rate 整体分布：
  - L1 < 0.5 → `knowledge-gap`（认知层有洞，需要补基础知识）
  - L1 ≥ 0.7 且 L2 < 0.4 → `lack-hands-on`（懂概念缺实操）
  - L1 ≥ 0.7 且 L2 ≥ 0.5 且 L3 < 0.3 → `lack-edge-thinking`（实操扎实但缺边界思考）
- 匹配度异常：扫所有场，若有 `match_score ≥ 75` 但 `overall_score × 20 < match_score - 15` 的→ `overestimated`
- 聚合规模：`interview_count < 3` → `small-sample`；`≥ 5` → `large-sample`
- 含 `aborted` 场 → `aborted-included`

## 步骤 3：写聚合文件

### 3.1 确定文件名

```
interviews/{今天日期}-summary.md          # 首次
interviews/{今天日期}-summary-v2.md       # 同日重新聚合
interviews/{今天日期}-summary-v3.md       # ...
```

`今天日期` 用当前日期，**不是某场面试的日期**。

冲突检测：

- 同日同名存在 → 自动 `-v2`，再存在 → `-v3`...
- **不删除旧文件**，让用户保留结论演进历史

### 3.2 拟字段预览（强制握手）

写文件**前**，把拟写入的关键字段表展示给用户确认：

```
即将生成聚合文件：
- 文件名：interviews/2026-05-11-summary.md
- 包含面试：[2026-05-08-bytedance-sre-p6, 2026-05-10-alibaba-sre-p7]
- 整体评分：3.1 / 5
- Top 3 补课主题：K8s 故障排查 / 系统设计容量 / Go 实战
- 维度评分：K8s 排障 2.0  Prometheus 4.0  系统设计 2.5  ...

确认生成？（yes / 修改 X / 取消）
```

- 用户回 `yes` / `确认` → 进 3.3
- 用户提出修改（如"K8s 那个维度评分我觉得不对"） → 调整后**再次预览**
- 用户取消 → 退出，不写文件

1. 中文、专业、数据导向
