# 简历项目问题与回答自查

帮助用户在简历完成后，先讲清自己的项目，再决定是否进入 `mock-interview`。支持独立使用，不要求简历来自其他 skill，不要求也不引入 JD。

## 选择阶段与来源

- 用户要求出题：执行阶段 A。
- 用户提供已填写的题单并要求评分：执行阶段 B。回答不完整也可以评估，不重新生成题目。
- 用户只想讨论方案：只分析，不创建文件。
- 优先使用用户指定的 PDF、Markdown、粘贴内容及项目范围。未指定项目时使用该份简历的全部项目；同一项目的技术版、业务版合并为一个项目，存在冲突则先核实。
- 未指定文件时可列出 `resumes/` 中的候选简历；多个候选且无法从上下文确定时，询问使用哪份，不擅自挑选。不要用 `Example/` 中的演示简历替代真实输入。
- 缺少来源、文件不可读或 PDF 提取不完整时，说明具体缺失并请求必要内容，不能猜测。使用可用的 PDF 工具提取内容，跨页项目要读完整；图片型 PDF 无可靠识别结果时暂停依赖该页的工作。
- 评估有题目和回答但缺原简历时，可以检查回答本身，注明“未核对原简历”；不要据此给出完整项目自查通过建议。

## 阶段 A：生成问题

### 1. 先识别项目证据

按项目读取背景、个人职责、实施过程、成果和约束。内部记录每个问题对应的原文位置或短引文；这些记录不放进脑图正文。

出题依据是**该项目明细**。专业技能栏、独立技术栈列表、其他项目、JD 和参考模板不能替代项目证据。项目明细只说“镜像扫描”，就问扫描的安排和处理，不预设用 Trivy；只说“容器监控”，就问指标和用途，不自行指定 cAdvisor。

允许围绕已有行动询问原因、实现、验证和合理的异常情境，但不暗示用户做过明细中未陈述的事。假设情境明确写“如果”。保留“参与、协助、负责”的职责边界，不升级为主导；不要新增规模、收益或事件。用户补充的项目事实可以成为新依据。

### 2. 按两个视角写独立问题

| 视角 | 关注内容 |
| --- | --- |
| 业务视角 | 服务对象、实际痛点、业务影响、目标优先级、职责分工、协作交付、验收标准、成果统计口径 |
| 技术视角 | 方案选择、链路、实施操作、配置与数据、故障定位、验证、回退、与项目直接相关的取舍 |

先业务后技术，每个视角默认 15 题，用户指定数量时按指定数量。每题聚焦一个主要问题，语言直接，不安排 L1/L2/L3 或连续追问。问题深浅取决于项目承担的工作，不机械套岗位年限。

业务题贴合真实场景，例如数据采集是否连续、内部发布效率或现场验收，不强行套营收。技术题检验项目操作与理解，不扩展成无关八股题。避免同视角换词重复，也避免两个视角重复问同一件事；同一行动可以分别问实现方法与业务影响。

如果项目描述过短，无法形成足量且不重复的问题，先告知该项目能支持的数量及缺失信息，让用户选择补充明细或减少题数。其他证据充分的项目可以继续；用户已允许少出题时直接按证据生成并在交付消息说明，不能为了凑数编造。

### 3. 输出可填写的四级 Markdown

仅保留以下层级。不要添加 front matter、第五级标题、来源节点、考察点、参考答案或说明章节，以免影响脑图结构。

```markdown
# 项目面试问题清单

## 项目名

### 业务视角

#### 这次改造优先解决什么实际问题？

回答：

### 技术视角

#### 发布失败时，你怎样恢复对应版本的镜像和配置？

回答：
```

项目名使用简历原名；问题不加编号，定位使用“项目名 / 视角 / 该视角第 N 题”。默认每题附空白 `回答：` 段落，用户直接在其后填写。用户明确只要纯脑图时省略回答占位，稍后评估仍支持问题下的普通段落或列表。不要把回答写成标题。

交付消息说明来源文件、所选项目、题数及填写方式。可说明是用于 XMind 导入的四级 Markdown；未经实际导入不要声称已验证 XMind 展示或回答备注行为。

### 4. 交付前核对

- 每题可追溯到本项目明细；没有技术栈列表独有的工具、跨项目移植或虚构经历。
- 项目、视角、题数和顺序正确，问题互不重复，没有隐含的参考答案。
- 使用 `scripts/check_questionnaire.py <题单.md> --expected-per-view 15` 检查结构；自定义数量时替换 15，各项目数量不同则省略该参数并人工核对。脚本只验证结构，内容依据仍需人工式逐题检查。

## 阶段 B：评估已填写回答

执行本阶段前阅读 [评分与报告规则](references/assessment.md)。

1. 只读题单和可用的原简历，按项目、视角及问题原文对应回答。不覆盖原始题单，不改写用户的话，不重排问题来回避缺答。
2. 先核对题目是否有项目依据。若沿用旧题单，出现技术栈列表独有技术或错误预设，将该题标为“题目不适用”，解释来源问题，不惩罚候选人。
3. 为每题区分已评分、未回答、待澄清、题目不适用。空白和占位不是 1 分；明确“不会”可评 1 分；事实矛盾单列证据，不能直接认定造假。
4. 按 1—5 分逐题引用证据评估，指出已覆盖、缺失或需澄清的内容，并给出具体补充方向。不代写候选人的经历或标准答案。短答、缺命令、术语少本身不是扣分理由。
5. 按项目与视角统计覆盖率、可评分题数和均分，列出关键问题的状态。最后给阶段性或整体准备度建议；不能以总平均分代替核心项目的判断。
6. 保存独立报告并说明评估范围。用户补答后重新生成版本，旧报告及旧回答均不覆盖。

## 保存与数据边界

- 默认保存到仓库根目录 `resumes/project-prep/`；`resumes/` 已被 gitignored，真实题单、回答和报告不放入公共示例或 skill 目录。
- 题单：`{来源名}_项目问题_{YYYY-MM-DD}.md`；评估：`{题单名}_评估_{YYYY-MM-DD}.md`。粘贴内容无文件名时用 `项目自查`，清理文件名中的路径分隔符。
- 文件已存在时追加 `-v2`、`-v3`，不覆盖；目录不存在时创建。用户指定其他保存位置则遵从其指示。
- 题单的来源在交付消息中记录；不要为了来源追踪破坏四级脑图。后续会话无法确定原简历时询问或按“未核对原简历”处理。
- 不创建或写入 `interviews/`，不复用模拟面试 schema，也不把书面自查当成真实面试记录或跨场能力证据。
- 用户只要求在对话中展示时不写文件。

## 下一步

准备度只针对当前书面回答，不代表经历已经被验证，也不等于匹配目标岗位或保证面试通过。报告建议是可选参考，不设置强制准入。

评估后，用户需要单题帮助时可转交 `interview-answer-coach`。提供原题单路径、项目名、视角、该视角第 N 题及可用的评估报告、原简历路径；原题单中的完整回答是辅导证据，报告只辅助定位。表达不清可展开已有思路，知识或实操不足需要补课练习，事实矛盾先核实，不能把低分一律当作润色问题。

辅导后由用户重新作答，再按阶段 B 生成新版评估；不把 coach 的建议当作用户已答内容，不自动提分，不覆盖旧回答或旧报告。

用户决定开始 JD 模拟面试后，再交给 `mock-interview`，由它检查简历、完整 JD 及自身前置条件。本 skill 不主动索要 JD，不自动开面，也不以自查分数替代 JD 匹配分。
