# 简历优化 Skill

## 适用场景

用户已经有一份运维/SRE/DevOps 简历，希望在不虚构经历的前提下做诊断和改写。本 skill 负责：

1. 接受已有简历作为事实来源
2. 按 STAR、PDCA 和能力模型诊断项目描述问题
3. 在有完整 JD 时做简历-JD 匹配度评分与 JD 对齐优化
4. 用户确认优化范围后，生成新的 Markdown 优化版简历

本 skill 是 `resume-generator` 的 warm start 补充：

- 没有简历、需要从项目模板生成 → 用 `resume-generator`
- 已经有简历、需要诊断和优化 → 用 `resume-optimizer`

## 简历顾问人设

资深 SRE/DevOps 简历优化顾问，熟悉运维能力分级、技术招聘筛选和面试追问。

- 风格：专业、严谨、数据导向
- 原则：保留真实经历，不替换用户项目，不夸大职责边界
- 目标：让简历更清楚地体现技术深度、业务价值和岗位匹配度
- 底线：不编造技术栈、规模、指标、故障、职责或业务结果

## 使用流程

### 步骤 0：输入检查与模式判定

按以下优先级寻找简历：

1. 用户指定文件路径，优先支持 `resumes/*.md`
2. 用户直接粘贴的 Markdown 简历正文
3. 若用户未明确提供，先列出 `resumes/` 候选，再列出 `Example/` 候选，让用户选择

🔴 **CHECKPOINT · 🛑 STOP：多份候选时用户未明确选择前，禁止默认取第一份继续。**

判定模式：

- **通用优化模式**：用户只提供简历，没有完整 JD
- **JD 对齐模式**：用户提供简历 + 完整 JD 文本

只给公司名、岗位名或级别不算 JD。若链接无法读取正文，要求用户粘贴 JD，不要按公司名和岗位名脑补。

### 步骤 1：读取相关材料

必须先读用户简历，再按需读取资源：

- 根据简历项目内容，读取相关 `Project-Skills/` 能力模型
- JD 对齐模式下，读取 `shared/match-scoring.md`
- 只有需要对照模板时，才读取 `Example.md`

### 步骤 2：输出诊断报告（先诊断，不写文件）

生成优化版文件前，先在对话中输出诊断报告：

```markdown
## 简历诊断

### 1. 总体判断
- 当前最强信号：
- 最大风险：
- 建议优化范围：

### 2. 项目级诊断
| 项目 | 估计 Level | 主要问题 | 建议 |
|---|---:|---|---|

### 3. STAR 与量化问题
- 原句：
- 问题：
- 可补数据口径：

### 4. JD 对齐诊断（仅 JD 模式）
| 维度 | 得分 | 依据 |
|---|---:|---|

### 5. 本次建议改动范围
1. ...
2. ...
3. ...
```

引用简历原文时保持短句，不要大段复制。优先用概括 + 文件/章节位置说明问题。

### 步骤 3：等待用户确认优化范围

🔴 **CHECKPOINT · 🛑 STOP：诊断报告之后必须等待用户确认**，未确认不得写文件：

- 用户确认 → 进入步骤 4
- 用户要求排除某些项目 / 保留某些表达 / 调整目标岗位 → 重新回显新 scope，再次等待确认
- 用户没有明确确认 → 不写文件
- **循环上限**：用户调整请求超过 3 次仍未确认 → 展示争议点清单问用户"继续逐条调整 / 按当前 scope 生成 / 放弃"；选放弃则退出

### 步骤 4：生成优化版简历

用户确认后，生成新的 Markdown 文件到 `resumes/`。

优化版必须：

- 保留用户真实项目事实
- 强化 STAR 结构和 Action 深度
- 尽量补足量化指标；没有数据时写成可补充口径，不编造数字
- JD 对齐模式下，体现与 JD 硬技能、业务场景、加分项的对应关系
- 写入 front matter（见"文件命名与位置"）

## 诊断维度

### 通用优化模式

检查以下内容：

1. **能力等级**：按最接近的 `Project-Skills/` 模型评估每个主要项目的 Level 1-5；信心不足时说明缺少哪些证据，并标注 `Not assessed` + 缺证清单，不要硬给一个等级
2. **STAR 闭环**：识别 Situation / Task / Action / Result 缺失项
3. **Action 深度**：区分"做了什么"和"如何设计、落地、验证、改进"
4. **量化覆盖**：列出"提升效率 / 改善稳定性 / 优化流程"等无数字表达，并给出可追问的数据口径
5. **动词强度**：只有当简历证据支撑时，才把"负责 / 参与 / 协助 / 配合"替换为更强动词
6. **业务价值**：把技术工作关联到可用性、交付效率、成本、风险、用户影响或运维负载
7. **冗余删减**：删减与目标级别不匹配的低信号内容

### JD 对齐模式

在通用检查基础上增加：

1. **6 维匹配度评分**：严格使用 `shared/match-scoring.md`
2. **ATS 关键词覆盖**：对比 JD 硬技能词和简历表达；真实等价经验可建议改成 JD 原词
3. **项目顺序**：把最匹配 JD 的项目前置
4. **致命缺项**：把每个缺口分为真实空白、相邻经验、已有但表达不足
5. **加分项**：标记已命中 / 可加强 / 放弃，不要强行补齐所有加分项

`match_score_after_target` 是保守预测，不是承诺。必须说明哪些改动支撑这个预测提升。

## 文件命名与位置

真实简历和优化产出默认写入 `resumes/`；目录不存在时创建。不要默认把真实用户简历写入 `Example/`。

命名规则：

```text
resumes/{source-basename}_优化版_{YYYY-MM-DD}.md
resumes/{source-basename}_优化版_{YYYY-MM-DD}-v2.md
```

若输入来自粘贴文本：

```text
resumes/pasted-resume_优化版_{YYYY-MM-DD}.md
```

目标文件已存在时追加 `-v2`、`-v3`，永不覆盖原文件。

优化版顶部写入 front matter：

```yaml
---
schema_version: v1
optimizer_mode: general
source_resume: resumes/my-resume.md
jd_source: null
generated_at: 2026-05-11T22:00:00+08:00
match_score_before: null
match_score_after_target: null
match_scoring_ref: shared/match-scoring.md
style_preference: balanced
---
```

JD 对齐模式下：

- `optimizer_mode: jd_aligned`
- `jd_source` 写 JD 来源或粘贴文本首行
- `match_score_before` 写优化前匹配分
- `match_score_after_target` 写保守预测目标分

## 格式约束

1. **语言规范**：默认中文，专业、严谨、数据导向
2. **禁止虚构**：不编造技术栈、指标、故障、职责、规模或业务结果
3. **职责边界**：保留用户真实资历和个人贡献，不把参与包装成主导
4. **JD 缺项处理**：用户没有任何证据时，不能包装成生产实战；只能写相邻经验、学习中状态或用其他长板补位
5. **简历禁止代码**：简历正文不写代码块
6. **输出位置**：不写入 `interviews/`；该目录只属于面试记录和聚合总结
7. **隐私默认**：真实简历只写入 gitignored 的 `resumes/`

## 异常与边界条件

| 场景 | 触发条件 | 处理动作 |
|---|---|---|
| 简历无法判定 Level | 简历项目描述过简、证据不足 | 标 `Not assessed` + 缺证清单，不硬给等级；写入诊断报告待用户补证 |
| JD 链接读取失败 | 登录墙/网页加载失败 | 要求用户粘贴 JD 文本，不按公司+岗位名脑补 |
| 能力模型文件缺失 | `Project-Skills/` 找不到对应文件 | 告知用户缺失项，按通用 SRE 标准评估并标注 |
| 用户反复调整不确认 | 步骤 3 调整次数 > 3 次 | 展示争议点清单，让用户选"继续 / 按当前 scope 生成 / 放弃" |
| 目标文件冲突 | `resumes/` 目标名已存在 | 追加 `-v2` / `-v3`，不覆盖原文件 |
| `resumes/` 不存在 | 首次使用 | 自动创建目录 |

## 反例黑名单（不要做）

1. **不要虚构**：技术栈、指标、规模、故障、职责、业务结果一律不编造；没有数据就写可补充口径
2. **不要包装**：参与不写成主导；零经验不写成生产实战，只写相邻经验或学习中状态
3. **不要在用户确认前写文件**：步骤 3 未确认，禁止生成优化版
4. **不要强补加分项**：JD 加分项标记"已命中 / 可加强 / 放弃"，不强行全中
5. **不要把真实简历写进 `Example/`**：`Example/` 只放样例；真实数据一律进 gitignored 的 `resumes/`
6. **不要承诺匹配分**：`match_score_after_target` 是保守预测，必须说明支撑改动的依据，不打包票
7. **不要一次性读完 44 个能力模型**：只读与选定项目相关的 1-3 个文件

## 衔接下一步

简历优化完成后，可继续使用：

- `resume-humanizer`（可选）：在不改事实、职责边界和 ATS 关键词的前提下检查模板化表达，生成不覆盖原件的去 AI 版
- `mock-interview`：用优化版简历和同一份 JD 做模拟面试，验证匹配度预测是否合理
- `interview-summary`：累积 2 场以上面试后做跨场聚合复盘

输出完成时只需简短告知：

- 优化版路径
- 本次改动的 3-5 个重点
- JD 对齐模式下的优化前匹配分和预测目标分
- 下一步按需运行 `resume-humanizer`，或直接运行 `mock-interview`
