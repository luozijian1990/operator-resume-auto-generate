# 张三 · 简历项目描述（技术演进视角）

> 虚构候选人示例。5 年 SRE 经验，覆盖金融科技 + 互联网两个行业；持续交付平台 + 监控告警平台两个核心项目。

## 项目一 · 企业级持续交付平台建设

**项目周期**：2023.03 - 2023.12（10 个月）
**所在公司**：某金融科技公司 · SRE 工程师（核心负责人）
**团队规模**：核心 5 人，协作 20+ 人
**技术栈**：Jenkins, Docker, Kubernetes, Harbor, GitLab, Helm, Prometheus, Grafana
**能力等级**：DevOps Level 1 → Level 3

### Situation

公司核心业务系统 32 个微服务，日均交易量 150 万笔。交付体系停留在 Level 1：

- 部署方式：SSH + SCP + Shell 手工启动
- 环境管理：仅有生产/测试两套，配置散落本地无版本化
- 构建流程：开发人员本地 Maven，产物通过企业微信传递
- 监控体系：依赖 Nginx 日志事后分析，无实时告警
- 版本控制：代码仓库与部署版本无关联

**关键风险指标**：

| 指标 | 现状 | 行业基准 |
|---|---|---|
| 部署频率 | 2-3 次/月 | 日级 |
| 单次部署耗时 | 4-6 小时 | <30 分钟 |
| 部署成功率 | 65% | >95% |
| MTTR | 2-4 小时 | <30 分钟 |
| 变更失败率 | 35% | <5% |

### Task

作为技术负责人，承担：

1. 容器化改造，实现应用与环境解耦
2. 端到端 CI/CD 流水线，覆盖代码提交到生产部署
3. 多环境治理，落地 dev/staging/prod 三套独立环境 + 配置版本化
4. 蓝绿/金丝雀发布能力，将单次发布耗时从小时级降到分钟级
5. 流水线可观测性，所有构建/部署事件可查可审计

### Action

事前规划阶段：盘点 32 个微服务的现状（Java/Python 混合栈），按业务重要性分批迁移；联合开发、测试、安全团队确认 Dockerfile 规范、镜像签名、漏洞扫描标准；制定回滚预案，保留传统 SSH 部署作为应急通道至少 2 个月。

事中实施阶段：基础设施层用 Kubeadm 自建 4 节点 K8s 集群（3 master + N worker），Harbor 作为私有镜像仓库并接入 Trivy 扫描；流水线层用 Jenkins 多分支流水线 + Helm Chart 模板化部署，按 GitFlow 分支模型自动触发对应环境的发布；发布层落地金丝雀（5% → 20% → 50% → 100%）和蓝绿两种策略，结合 Prometheus 实时观察 RT / 错误率自动判定升级或回滚；可观测层接入 Loki + Grafana，所有 Pipeline 事件、镜像构建记录、Deployment 状态汇总到统一面板。

事后验证阶段：发起为期 2 周的全量切换演练，对 32 个服务分批迁移；每完成一批做一次故障复盘和文档更新；最终全量交付时保留 1 周双轨运行（新旧并存）确认稳定。

### Result

| 核心指标 | 改进前 | 改进后 | 提升 |
|---|---|---|---|
| 部署频率 | 2-3 次/月 | 35+ 次/周 | 50x |
| 单次部署耗时 | 4-6 小时 | 8-15 分钟 | 30x |
| 部署成功率 | 65% | 97.2% | +32.2pp |
| MTTR | 2-4 小时 | 18 分钟 | 10x |
| 变更失败率 | 35% | 3.8% | -31.2pp |

**技术资产沉淀**：通用 Helm Chart 模板库（覆盖 Java/Python/Go 三种 runtime）、流水线规范文档（含 16 个 Stage 模板）、回滚 SOP、漏洞扫描准入门禁。该项目获公司年度技术创新奖。

## 项目二 · 监控告警智能化平台建设

**项目周期**：2024.05 - 2024.12（8 个月）
**所在公司**：某互联网中型公司 · SRE 工程师（项目负责人）
**团队规模**：核心 3 人，协作 15+ 人
**技术栈**：Prometheus, Grafana, AlertManager, Loki, VictoriaMetrics, Python, OpenTelemetry
**能力等级**：监控可视化 Level 1 → Level 3

### Situation

跨 200+ 服务的告警系统处在 Level 1：

- 监控埋点散乱，无统一标准（部分服务用 Zabbix、部分用 Prometheus、部分无埋点）
- 告警规则人工维护在 yaml，无 review 流程
- 告警风暴：高峰时 1 小时 800+ 条，工程师疲劳直接静音
- 告警准确率 ~40%，大量重复告警和无效告警

**风险**：真实故障被淹没在噪声里，2024 年 Q1 一次数据库慢查询造成业务 3 小时影响才被发现。

### Task

1. 监控埋点统一规范，所有新服务必须暴露 Prometheus metrics + 关键四金指标
2. 告警规则代码化，纳入 GitOps 工作流并接入审批
3. 告警聚合降噪，目标准确率 > 85%，单工程师值班期间告警量 < 50/天
4. 故障定位提速，关键告警必须 5 分钟内可定位到模块

### Action

事前规划：调研业界方案（USE Method、RED Method、Google SRE 四金指标），结合公司业务定 8 个核心指标维度；联合架构组定 OpenTelemetry SDK 接入规范；定告警分级（P0/P1/P2/P3）和响应 SLA。

事中实施：监控数据层用 VictoriaMetrics 替换 Prometheus 长存储以应对 1.5TB/天的写入；告警规则全部迁到 GitOps 仓库，PR 必须经过 SRE + 业务方双 review；落地告警分组、抑制、静默规则（基于 AlertManager + 自研规则引擎），同源告警 5 分钟窗口聚合为一条；故障定位层接入 Loki 做日志关联 + Trace ID 串联，关键告警直接附带链路上的最慢 Span 信息。

事后验证：每周告警准确率盘点会议 + 月度告警价值评审（删除 30 天内零次有效触发的规则）；针对每个 P0 告警建立 Runbook 索引并自动附加到告警卡片。

### Result

| 核心指标 | 改进前 | 改进后 | 提升 |
|---|---|---|---|
| 告警准确率 | 40% | 89% | +49pp |
| 单工程师值班告警量 | 200+/天 | 35/天 | -82.5% |
| 告警风暴峰值 | 800+/小时 | 60/小时 | -92.5% |
| 关键告警定位时长 | 35 分钟 | 4 分钟 | -88.6% |
| 监控埋点覆盖率 | 65% | 98% | +33pp |

**技术资产沉淀**：OpenTelemetry 接入 SDK + 内部脚手架、告警规则 PR 模板（含必填的 Runbook、误报止损步骤）、告警价值评审 SOP、内部培训课程。
