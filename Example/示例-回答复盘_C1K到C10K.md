# Interview Answer Coaching
## 原问题
系统 QPS 从 1K 增长到 10K，你会怎么处理？
## 原始回答
我会先看业务场景，不会直接上来就说 CDN、HPA、KEDA。流量通常有业务前兆，例如直播人数、活动预约人数；可预测时提前扩容，并准备限流、降级、异步等预案。无状态后端好扩，真正困难的是 DB 等有状态组件，所以单纯依赖 KEDA 效果一般。
## 一、你已经回答到的内容
业务场景、流量来源、可预测性、业务指标、容量规划、预扩容、限流、降级、异步、DB 瓶颈和 KEDA 边界。
## 二、已有但表达过度压缩的推理
“业务有前兆”已经暗含：业务事件 → 用户规模 → 请求规模 → 容量需求 → 预扩容。这是基于原话的架构推演，不等同于用户明确陈述的线上经历。“DB 难扩”还可展开为应用扩容 → 连接数和下游请求增加 → DB/Redis/MQ/第三方成为瓶颈。
## 三、真正缺失的内容
未体现平均/峰值/瞬时 QPS、读写比例、下游请求放大系数、压测安全水位和验证方式。这些是当前没体现的内容，不等于前述容量思路不存在。

## 六、30 秒回答版本
我会先判断业务场景和流量是否可预测，再看业务指标能否支持提前扩容。然后按入口、无状态服务和 DB 等有状态组件看整条链路，准备限流、降级和异步削峰。HPA/KEDA 只能解决部分无状态资源，不能替代下游容量规划。
## 七、90 秒回答版本
我会先确认业务场景，以及流量是否有可观测的业务前兆，再用业务指标做容量预测和预扩容。接着按入口、无状态服务、DB、缓存、MQ 和第三方逐段看容量，因为应用扩容不代表下游一定能承受。突发流量时准备限流、降级和异步削峰。HPA/KEDA 主要解决部分计算资源，不能替代 DB 等有状态组件的容量规划。

**建议补充（当前回答未体现）**：下一轮可以增加平均/峰值/瞬时 QPS、读写比例、下游请求放大系数，以及压测和安全水位的验证方法；没有真实数据时只说明方法。
